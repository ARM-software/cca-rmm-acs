
# Arm RMM ACS Device Assignment Testcase checklist
-----------------------------------------------------

This document presents the mapping of the rules in the RMM specification to the
test cases and the steps followed in the tests. This also provides the information
about the test coverage scenarios that are implemented in the current release of
ACS and the scenarios that are planned for the future releases.

| Test Number | Test Name | Test Assertions | Test Approach | Validated by ACS |
| --- | --- | --- | --- | --- |
| 1 | da_offchip_pcie | Device Assignment for offchip pci device | 1.Host: PCIe enumeration and device discovery<br>- Boot in NS Host.<br>- Initialize PCIe and perform enumeration.<br>- Read RMI_FEATURES and confirm DA support.<br>- Find a PCIe endpoint with DOE capability.<br>- Identify the Root Port and Endpoint.<br>- Discover BAR/MMIO ranges for the selected device.<br><br>2.Host: Create PDEV and establish secure communication<br>- Allocate/delegate granules for PDEV and its aux objects.<br>- Populate PDEV parameters.<br>- Call RMI_PDEV_CREATE. Call RMI_PDEV_GET_STATE and verify PDEV_NEW.<br>- Call RMI_PDEV_COMMUNICATE until device identity evidence is retrieved.<br>- Cache the device identity evidence.<br>- If SPDM communication is used, extract the device public key from the cached certificate chain.<br>- Call RMI_PDEV_SET_PUBKEY. Call RMI_PDEV_GET_STATE and verify PDEV state is PDEV_HAS_KEY.<br>- Continue RMI_PDEV_COMMUNICATE until PDEV state reaches PDEV_READY.<br><br>3.Host: Configure traffic protection<br>- Create the required protected stream between the Root Port and Endpoint.<br>- Populate stream connection parameters with stream_type = NCOH, pdev_1 = Endpoint PDEV, pdev_2 = Root Port PDEV, ide_sid = IDE stream ID, and addr_range = device non-coherent address ranges.<br>- Call RMI_PDEV_STREAM_CONNECT and save stream_hnd.<br>- Call RMI_PDEV_COMMUNICATE on Root Port PDEV while stream_wait is indicated.<br>- Call RMI_PDEV_COMMUNICATE on Endpoint PDEV while stream_wait is indicated.<br>- Continue required communication until both PDEVs complete the stream operation.<br>- Call RMI_PDEV_STREAM_COMPLETE with pdev_1 = Endpoint PDEV, pdev_2 = Root Port PDEV, and stream_hnd.<br>- Verify the stream reaches PDEV_STREAM_CONNECTED and both PDEV ops return to PDEV_OP_NONE.<br>- Verify traffic protection is configured for traffic between the SoC/Root Port and Endpoint device.<br>- If stream connection fails, do not continue with VDEV assignment for that device.<br><br>4.Host: Create Realm and VDEV<br>- Create a Realm with DA enabled.<br>- Allocate/delegate granules for VDEV and its aux objects.<br>- Call RMI_VDEV_CREATE only after the PDEV stream reaches PDEV_STREAM_CONNECTED. Call RMI_VDEV_GET_STATE and verify VDEV_NEW.<br>- Call RMI_VDEV_COMMUNICATE until VDEV state reaches VDEV_UNLOCKED.<br>- Call RMI_VDEV_LOCK. Call RMI_VDEV_COMMUNICATE until VDEV state reaches VDEV_LOCKED.<br>- Call RMI_VDEV_START. Call RMI_VDEV_COMMUNICATE until VDEV state reaches VDEV_STARTED.<br><br>5.Host: Collect device attestation evidence<br>- Call RMI_VDEV_GET_MEASUREMENTS. Complete required RMI_VDEV_COMMUNICATE. Cache the measurements.<br>- Call RMI_VDEV_GET_INTERFACE_REPORT. Complete required RMI_VDEV_COMMUNICATE. Cache the interface report.<br>- Check RMM stores digests of Host-cached attestation evidence.<br><br>6.Realm: Verify device information<br>- Realm boots and checks RSI_FEATURES for DA support.<br>- Host passes vdev_id to Realm.<br>- Realm calls RSI_VDEV_GET_INFO.<br>- Realm requests device identity evidence, device interface report, and measurements from Host.<br>- Realm verifies digests from RMM against Host-cached evidence.<br>- If SPDM communication is used, Realm checks that public key digest matches public key in device certificate chain.<br>- Realm validates negotiation data, device identity evidence, and device measurements.<br>- Realm decodes the interface report and extracts MMIO ranges.<br><br>7.Host/Realm: Validate mappings<br>- Realm requests mapping validation for each MMIO range using RSI_VDEV_VALIDATE_MAPPING.<br>- Host observes RMI_EXIT_VDEV_MAP exits.<br>- For each exit, Host validates REC exit fields.<br>- If mappings are not present, Host maps device memory using RMI_RTT_DEV_MAP.<br>- Host calls RMI_RTT_DEV_VALIDATE.<br>- Check RTT entries are RTTE_NARCH_DEV.<br>- Check validated IPA range becomes RIPAS=DEV.<br>- Realm repeats RSI_VDEV_VALIDATE_MAPPING until validation completes for the requested range.<br>- Realm confirms the mappings are valid for the reported IPA ranges.<br><br>8.DMA disabled check<br>- DMA state of a VDEV is VDEV_DMA_DISABLED.<br>- When Realm performs DMA using the test engine from source buffer to destination buffer in Realm memory, the SMMU blocks traffic from the device to the Realm protected IPA space.<br><br>9.Realm: Enable DMA and Realm verify data movement<br>- Realm calls RSI_VDEV_DMA_ENABLE.<br>- Realm performs DMA using the test engine from source buffer to destination buffer in Realm memory.<br>- Realm verifies DMA success by comparing source and destination buffers.<br><br>10.Teardown<br>- Realm calls RSI_VDEV_DMA_DISABLE.<br>- Host unmaps device memory using RMI_RTT_DEV_UNMAP.<br>- Verify RTT entries become RTTE_VOID.<br>- Verify RIPAS becomes DESTROYED when previous RIPAS was DEV.<br>- Host tears down VDEV:<br>&nbsp;&nbsp;- RMI_VDEV_UNLOCK<br>&nbsp;&nbsp;- RMI_VDEV_DESTROY<br>- Host tears down PDEV:<br>&nbsp;&nbsp;- RMI_PDEV_DESTROY | Yes |
